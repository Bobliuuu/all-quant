# Related work: where UltraQuant-style fused FP4 KV decode sits

Status of claims: **[V]** = read this session from the cited page (via a fetch tool that summarises pages, so figures are as relayed, not re-checked against PDFs); **[M]** = from memory / not re-fetched, treat as unverified; **[U]** = could not verify. No numbers here are measured by this repo unless stated.

## 1. The reference points

**UltraQuant paper** (arXiv 2606.20474, "UltraQuant: 4-bit KV Caching for Context-Heavy Agents", AMD + UCLA, June 2026) [V]: https://arxiv.org/abs/2606.20474 , https://arxiv.org/html/2606.20474v3
- Format: FP4 E2M1 codes, one UE8M0 scale per 32 channels (17 B per group, 4.25 bit/elt). Per-group scale `E = round(log2(c * absmax))` with one global constant `c = 0.156` (MSE-optimal on rotated keys; `c=0.195` erased the gain over FP8, `c=1.0` was 4.3 pp worse than FP8 on their ablation).
- Keys are Walsh-Hadamard rotated, values are not. Queries are rotated into the key basis and cast to FP8 E4M3. First and last two attention layers stay BF16 (n=2).
- Kernel: `v_mfma_scale_f32_16x16x128_f8f6f4` on CDNA4 reads FP4 K, FP8 Q and UE8M0 scales in one instruction (no BF16 K materialised); V path uses a hardware FP4/UE8M0 -> BF16 conversion; FP8 query hoisted out of the K-tile loop; FlyDSL implementation inside vLLM. Kernel not released as of the paper.
- Reported (all MI355X): decode 1.38x BF16 throughput vs 1.37x for FP8 KV (MiniMax-M2.5, 32K in/1K out, C=64); decode-attention time 1.18x of FP8's at 32K, batch 8 (Ultra-TQ 2.45x); multi-turn ShareGPT/Gutenberg C=32: 3.47x P50 TTFT in late rounds, 1.63x output throughput vs FP8; Claude-Code trace replay: 2.71x (MiniMax) / 4.38x (Qwen3-235B) cumulative qualified requests vs BF16; 3.2-3.4x BF16 logical KV capacity.
- Honest limits stated: speed advantage over FP8 only appears when FP8's resident cache is exceeded; at short context 4-bit pays ~1-3%; single global `c`; SWE-bench Lite MiniMax 62 (BF16) / 62 (FP8) / 59 (UltraQuant), Qwen3-235B 28 / 21 / 24; official RULER MiniMax-M2.5 74.03 -> 67.08.
- **Unverified / inconsistent between my two reads of the paper:** one read reported AIME25 regressions of -13.3 pp (Qwen3.5-A3B) and -10.0 pp (MiniMax); another reported MiniMax AIME25 -0.84 pp (5 seeds). Also, "1.63x vs FP8" appears in the abstract for UltraQuant and, separately, as the TQ4/4 vs FP8 total-throughput ratio (28,539 vs 17,536 tok/s) in AMD's TurboQuant blog. Re-read the PDF before quoting any of these.

**Upstream vLLM backend** [V, source read 2026-11-12, not run by us]: vLLM PR #57057 "[Attention] Add UltraQuant 4-bit KV cache backend (FlyDSL D=256)", merged 2026-10-06; `--kv-cache-dtype ultraquant_4bit`, `vllm/v1/attention/backends/ultraquant_attn.py`. Listed in the ROCm platform's backend candidates only (`platforms/cuda.py` and `xpu.py` have no UltraQuant reference); FlyDSL decode needs gfx950 and head_dim 256 (GQA 6/8/16), other shapes use a Triton unified kernel (QK written for CDNA4 scaled FP4 MFMA); bf16 queries only; no attention-sink models. Its decode and small-chunk continuation paths call the kernel with `max_query_len=1` (single-query rows; no K-query read sharing in the paths read). Whether the Triton fallback works on CUDA or Intel was not tested.

**AMD ROCm blog "UltraQuant on AMD Instinct: More Efficient Agentic Serving for Qwen3.8-MXFP4"** (25 Sep 2026) [V]: https://rocm.blogs.amd.com/software-tools-optimization/ultraquant-kv4/README.html
- 8x MI355X, vLLM 0.19.2rc0 + AITER + FlyDSL 0.2.0, Qwen3.8-2.4T-A95B MXFP4 weights; only 23 of 92 layers carry a KV cache (hybrid), UltraQuant only applies there. Replayed SemiAnalysis InferenceX agentic trace, prefix hit 91-95%.
- C=32: 434 tok/s @ 58 ms vs ROCm-FA 8-bit 338 tok/s @ 77 ms (+29%) and AITER-unified 8-bit 307 tok/s (+41%); decode-attention kernel 2.25x faster at 32K; even at C=4-8.
- MTP: each verify step scores 3 positions, ~2.3 tokens committed. vLLM expands verification into B*K single-token query rows; the UltraQuant decode kernel treats them as independent queries (no cache-read sharing) whereas the 8-bit path uses AITER's fused K-query `unified_attention`. Quote: "A fused K-query UltraQuant kernel could share cache reads across candidate positions and is an opportunity for further optimization." At C=32 both MTP arms regress. **This is exactly the gap `uqmt/attn.py` fills.**
- GPQA-Diamond: 8-bit 94.4, 8-bit+MTP 92.9, UltraQuant 92.9, UltraQuant+MTP 91.4 (authors: within noise). SWE-bench Lite (100 tasks): 8-bit 78 / 81 (+MTP), UltraQuant 81 / 88.

**SGLang PR #41949, UltraQuant MXFP4 KV backend** [V]: https://github.com/sgl-project/sglang/pull/41949 (open; approved 20 Oct 2026, CI red at last look). `--kv-cache-dtype ultraquant_4bit --attention-backend ultraquant`; fused rotate+quantise+scatter store kernel; FlyDSL decode for head_dim 256 / GQA 6,8,16 else Triton FP4; native FP4 Triton extend. gfx950 + bf16 MHA/GQA only; startup rejects **speculative decoding**, MLA, sliding-window hybrids, LMCache, hierarchical cache, disaggregation, PP>1. GPQA-D 85.86 vs 84.85 (Qwen3.6-27B), 86.74 vs 87.75 (Qwen3.5-397B). Throughput only 1.05-1.13x FP8 at C=32-40.

**AMD TurboQuant blog and LMCache blog** [V]: https://rocm.blogs.amd.com/artificial-intelligence/turboquant-vllm-agentic/README.html , https://rocm.blogs.amd.com/software-tools-optimization/4bit-KV-LMcache/README.html . TQ4/4 (WHT on keys only, no QJL, first/last layers BF16), 134 B/token/head packed; LMCache: 3.76x smaller than BF16, 2.0x requests completed in 20 min, p95 TTFT 140 s -> 53 s, HBM-resident tokens 201,280 -> 648,064, RULER 16k/64k/128k DRAM reload within +0.4/-0.1/0.0 of HBM-served; layout-aware connector for mixed BF16/4-bit layers; docker `rocm/vllm-dev:quark-ultraquant-lmcache-mi355`. Note: this LMCache work is TurboQuant, not UltraQuant ("UltraQuant presets with LMCache" is listed as future work).

## 3. Observations that matter for this repo

1. **Nobody has a published fused K-query FP4 decode kernel.** AMD's blog names it as the open opportunity; SGLang's UltraQuant backend rejects speculative decoding outright; the 8-bit path has one (AITER `unified_attention`). Our `fused=True` kernel is a direct answer. Measured here (results/mi300x_b8_c32k_tuned.json, B=8, ctx 32768, Hq64/Hkv8/D128): fused vs K independent queries 0.98x / 1.83x / 2.59x / 4.10x at K=1/2/4/8.
2. **The scale that matters is per-block absmax, not the codebook** (paper ablation B.1: per-token L2 0.6237 -> per-block absmax 0.6559 on GPQA, Lloyd vs uniform within noise; single seed, sigma ~1.7 pp). Our `quantize_fp4` uses `ceil(log2(amax/6))` (no clipping, c = 1/6 = 0.167 scaled to the next power of two), while the paper picks `round(log2(0.156*amax))`, which clips the top of the block deliberately. The paper's c=0.195 case matching FP8 and c=1.0 losing 4.3 pp shows scale choice is first-order. We have not measured task accuracy at all.
3. **Rotation is what makes 4-bit keys work** (paper: tuned centroids without rotation leave ~2.3x the MSE). Our code has no rotation. K-Hadamard needs the query rotated too (an orthogonal H leaves q.k invariant) so it can live outside the kernel.
4. **Gains are regime-dependent**: UltraQuant beats FP8 mainly once FP8 cannot keep the prefix resident; at short context it pays a few percent. USE_CASES.md reflects this.
5. **QServe's trick (keep Q unquantised, smooth K)** and the UltraQuant FP8-query path are different philosophies; on MI300X (no FP8 x FP4 scaled MFMA) our measured experiment (UQ_FP8K flag, results/mi300x_tuning_notes.md) shows the fp8-query path is slower (K=8 0.66 vs 0.54 ms) and noisier (4e-3 vs 3e-4 max error).
6. Not verified this session: KIVI, KVQuant, Atom, QuaRot, SpinQuant, H2O, SnapKV, Quest, Medusa, EAGLE-3 details and numbers (cited from memory; arXiv ids given for lookup); SGLang EAGLE tree-verify kernel (search returned nothing); vLLM tree-verify path; vLLM/SGLang FP8-KV flag specifics; exact PolarQuant definition.

## 4. Additions requested later: SemKV, StarKV, 2026 FP4 KV methods, code availability

Machine-readable version with repos, default-branch HEAD commits (from `git ls-remote`, 2026-11-11, not audited), install and entry points: `docs/methods.json`. Install commands marked `[unverified]` there were not read this session; pin and test before relying on them.

- **SemKV** [V from abstract page only]: arXiv 2608.28911, "SemKV: Semantic Mixed-Precision KV Cache Quantization Guided by the Quality Cliff" (https://arxiv.org/pdf/2608.28911). Keeps every token, ranks by a model-internal importance score, assigns two adjacent precisions above a "quality cliff" (~2.322 code bits for Llama-3.1-8B-Instruct, affine quantiser; collapse at 2.0). Reports 6.0x storage with no detectable quality difference (n=900, 3 seeds); 7.9x with a TurboQuant-MSE base quantiser. **No public code found** after two searches and the abstract page; the quality agent must reimplement it (a per-token two-level bit assignment is simple on top of a fake-quant harness). Name collisions to avoid: SemanticKV arXiv 2611.11452 (video generation eviction) and SeKV arXiv 2606.31145 (code: AmirAbaskohi/SeKV).
- **StarKV**: the match is **STAR-KV**, ICML 2026 spotlight, arXiv 2606.08382, "Low-Rank KV Cache Compression via Soft Thresholding for Adaptive Rank Control" (https://arxiv.org/pdf/2606.08382). It is low-rank (caches projected activations with learned per-head/block rank, trained with distillation) plus optional 3.2-bit quantisation (20% channels at 4 bit, rest 3 bit after Hadamard). It is **not** Star Attention (no Star Attention KV method found under that name). Code: https://github.com/PriyanshBhatnagar/STAR-KV (self-described official; Python 3.12.7, `train.py`, `eval.py --kv-quant --triton`, `latency.py`; Triton decode MHA-only, GQA models only via fake-quant; no licence file visible); vLLM variant STAR-KV-Serve. Claims (press release / README, unverified by me): up to 75% reduction, 20x with quantisation, 6.9x attention speedup, 3.1x e2e throughput. Needs per-model training, so it is a poor fit for a quick quality comparison; treat as a stretch target.
- **BitDecoding-FP4** (arXiv 2611.09825, Nov 2026) [V from search abstract]: native FP4 KV decoding, NVFP4 within 0.5 pt and MXFP4 ~1 pt of BF16 KV, dense/MoE, GQA and MLA. Code MIT: https://github.com/OpenBitSys/BitDecoding-FP4 ; **B200/B300 only, CUDA 13+, Python 3.12, vLLM out-of-tree backend**; no ROCm. Most direct CUDA comparator for our B300 numbers.
- **ScaleSearchAttention** (arXiv 2605.12464): NVFP4 KV with QK^T and PV in NVFP4 on tensor cores; no code link found [U].
- **Diagnosing FP4 inference: layer-wise and block-wise sensitivity of NVFP4 vs MXFP4** (arXiv 2603.08747) and **Bridging the Gap Between Promise and Performance for Microscaling FP4 Quantization** (arXiv 2509.23202): weight/activation focused, useful for the MXFP4-vs-NVFP4 scale question (gap 7); not read [U].
- **kvpress (NVIDIA)** [V]: Apache-2.0 harness for ~40 eviction/compression "presses" (SnapKV, PyramidKV, StreamingLLM, ExpectedAttention, KVzip, ...) plus `QuantizedCache(backend="quanto", nbits=4)`; Llama/Mistral/Phi3/Qwen2/Qwen3/Gemma3; CUDA in examples. It is the practical way to run eviction baselines on real models; its 4-bit quanto cache is a simple (non-FP4, non-fused) quantisation baseline.
- **Public-code summary for the quality agent**: ready to run now: kvpress (all eviction + quanto-4bit), BitDecoding-FP4 (B300 only), QuaRot (Hadamard utilities), amd-experiments (MI300X, TQ/Iso/Planar/Rotor), KIVI, KVQuant, Atom, QServe, SpinQuant, SageAttention (repos exist per `git ls-remote`; run recipes unverified). No public code: UltraQuant kernels (SGLang PR open only), SemKV, AMD's TurboQuant vLLM kernels (blog links no repo).
